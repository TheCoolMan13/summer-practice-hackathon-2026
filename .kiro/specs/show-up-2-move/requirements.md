# Requirements Document

## Introduction

ShowUp2Move is a smart social sports-matching platform that enables users to quickly organize spontaneous sports activities with others nearby. Users create lightweight profiles, declare daily availability with a single tap, get automatically matched into sport-appropriate groups, coordinate logistics through group chat, and ultimately show up and play. The platform includes a React web frontend, a Node.js/Express backend with PostgreSQL, real-time communication via Socket.IO, and an optional Python FastAPI AI microservice that enhances — but never blocks — core functionality.

---

## Glossary

- **Auth_Service**: The backend module responsible for user registration, login, JWT issuance, and token validation.
- **Profile_Service**: The backend module responsible for creating and updating user profiles.
- **Feed_Service**: The backend module responsible for aggregating and serving the home activity feed.
- **Availability_Service**: The backend module responsible for recording, expiring, and querying user availability.
- **Matching_Engine**: The backend module responsible for automatically grouping available users into sport-appropriate groups.
- **Captain_Selector**: The sub-component of the Matching_Engine responsible for assigning a captain to each generated group.
- **Group_Service**: The backend module responsible for managing group membership, status, and lifecycle.
- **Chat_Service**: The backend module responsible for real-time group messaging via Socket.IO.
- **Event_Service**: The backend module responsible for manually created events and their lifecycle.
- **Notification_Service**: The backend module responsible for delivering real-time and scheduled notifications.
- **Location_Service**: The backend module responsible for proximity calculations and venue discovery.
- **AI_Service**: The separate Python FastAPI microservice providing AI-powered enhancements.
- **User**: A registered and authenticated person using the platform.
- **Captain**: The User assigned coordination responsibility for a matched group.
- **Group**: A set of Users matched together to play a specific sport.
- **Event**: A sports activity — either auto-generated by the Matching_Engine or manually created by a User.
- **Availability_Window**: The time period during which a User's availability declaration is considered active (default: 8 hours).
- **JWT**: JSON Web Token used for stateless authentication.
- **Feed**: The home screen list of upcoming and nearby Events visible to a logged-in User.
- **Compatibility_Score**: A numeric value (0.0–1.0) produced by the AI_Service indicating how well two Users are likely to play together.

## Requirements

### Requirement 1: User Registration

**User Story:** As a new visitor, I want to register an account, so that I can access the platform and start joining sports activities.

#### Acceptance Criteria

1. WHEN a visitor submits a registration form with a unique email, a username, and a password of at least 8 characters, THE Auth_Service SHALL create a new User account and return a JWT.
2. WHEN a visitor submits a registration form with an email that already exists, THE Auth_Service SHALL return an error message stating that the email is already in use.
3. THE Auth_Service SHALL store passwords as bcrypt hashes with a minimum cost factor of 10 and SHALL NOT store plaintext passwords.
4. THE Auth_Service SHALL NOT include password hashes or plaintext passwords in any API response.
5. WHEN a User account is successfully created, THE Auth_Service SHALL complete the registration flow within 3 seconds under normal load.

---

### Requirement 2: User Login

**User Story:** As a registered user, I want to log in, so that I can access my profile and platform features.

#### Acceptance Criteria

1. WHEN a User submits valid credentials (email and password), THE Auth_Service SHALL return a signed JWT with an expiry of 24 hours.
2. WHEN a User submits invalid credentials, THE Auth_Service SHALL return an error message stating that the email or password is incorrect, without revealing which field is wrong.
3. WHEN an unauthenticated User attempts to access a protected route, THE Auth_Service SHALL return a 401 response with a message explaining which feature requires login.
4. THE Auth_Service SHALL redirect unauthenticated Users to the login page with a descriptive message rather than a generic error.

---

### Requirement 3: User Profile Creation and Editing

**User Story:** As a registered user, I want to create and update my profile, so that the platform can match me with compatible sports partners.

#### Acceptance Criteria

1. WHEN a User submits a profile with a display name and at least one preferred sport, THE Profile_Service SHALL save the profile and return the updated User record.
2. THE Profile_Service SHALL accept the following optional profile fields: short bio (max 280 characters), profile picture URL, skill levels per sport (beginner / intermediate / advanced), and location coordinates.
3. WHEN a User submits a profile update, THE Profile_Service SHALL complete the update within 2 seconds under normal load.
4. THE Profile_Service SHALL NOT overwrite a User's manually selected sports preferences with AI-inferred suggestions without explicit User confirmation.
5. WHEN a User uploads a profile picture, THE Profile_Service SHALL accept JPEG and PNG files up to 5 MB and store a publicly accessible URL.

---

### Requirement 4: AI-Assisted Profile Understanding

**User Story:** As a user, I want the platform to suggest sports based on my bio, so that I can set up my profile faster.

#### Acceptance Criteria

1. WHEN a User submits a bio text to the AI_Service `POST /extract-interests` endpoint, THE AI_Service SHALL return a list of inferred sport names within 5 seconds.
2. WHEN the AI_Service is unavailable, THE Profile_Service SHALL return an empty suggestions list and allow the User to select sports manually without displaying an error that blocks profile creation.
3. THE Profile_Service SHALL present AI-inferred sport suggestions as selectable options and SHALL require explicit User confirmation before adding them to the profile.
4. WHEN a User uploads a profile picture, THE AI_Service SHALL optionally analyze the image and return inferred sport interests, subject to the same confirmation requirement in criterion 3.

---

### Requirement 5: Home Feed — Activity Discovery

**User Story:** As a logged-in user, I want to see upcoming sports activities on my home feed, so that I can quickly find and join events.

#### Acceptance Criteria

1. WHEN a logged-in User loads the home feed, THE Feed_Service SHALL return a list of upcoming Events sorted by start time ascending, including: sport type, current participant count, required group size, start time, location name, organizer/captain display name, and the User's participation status.
2. WHEN a logged-in User applies a sport filter, THE Feed_Service SHALL return only Events matching the selected sport type.
3. WHEN a logged-in User applies a distance filter with a radius in kilometers, THE Feed_Service SHALL return only Events whose location is within the specified radius of the User's stored location.
4. WHEN a logged-in User applies a time filter, THE Feed_Service SHALL return only Events starting within the specified time window.
5. WHEN no Events match the current filters, THE Feed_Service SHALL return an empty list and THE frontend SHALL display an empty state message encouraging the User to create or join an activity.
6. WHEN a logged-in User taps "Join" on an Event with available capacity, THE Event_Service SHALL add the User to the Event's participant list and return the updated participant count.

---

### Requirement 6: Availability Declaration — "ShowUpToday?"

**User Story:** As a user, I want to declare my availability for sports today with a single tap, so that the platform can match me with others quickly.

#### Acceptance Criteria

1. WHEN a User taps "Yes" on the "ShowUpToday?" prompt, THE Availability_Service SHALL record the User as available and set an expiry timestamp equal to the current time plus 8 hours.
2. WHEN a User taps "No" on the "ShowUpToday?" prompt, THE Availability_Service SHALL record the User as unavailable and SHALL NOT include the User in matching runs.
3. WHEN a User declares availability, THE Availability_Service SHALL optionally accept a preferred time window (start time and end time) and a list of sports for that day.
4. WHEN a User's availability expiry timestamp is reached, THE Availability_Service SHALL automatically mark the User as unavailable.
5. THE Availability_Service SHALL complete a Yes/No availability update within 1 second under normal load.
6. WHEN a User has an active availability declaration, THE frontend SHALL display the User's current availability status and remaining time on the availability prompt.

---

### Requirement 7: Smart Matching

**User Story:** As an available user, I want to be automatically matched into a sports group, so that I can play without manually coordinating with others.

#### Acceptance Criteria

1. WHEN the Matching_Engine runs, THE Matching_Engine SHALL group available Users by their shared sport preferences and form Groups that meet the minimum group size for that sport (Football: 10, Basketball: 6, Tennis: 2, Volleyball: 8).
2. WHEN the Matching_Engine forms a Group, THE Matching_Engine SHALL not exceed the maximum group size for that sport (Football: 14, Basketball: 10, Tennis: 4, Volleyball: 12).
3. WHEN location data is available for all candidate Users, THE Matching_Engine SHALL prioritize grouping Users within a 10 km radius of each other.
4. WHEN skill level data is available, THE Matching_Engine SHALL prefer grouping Users with compatible skill levels (within one tier of each other).
5. WHEN the AI_Service is available, THE Matching_Engine SHALL request compatibility scores from `POST /profile-compatibility` and use them as a secondary ranking signal; WHEN the AI_Service is unavailable, THE Matching_Engine SHALL proceed with matching using only sport, availability, location, and skill criteria.
6. WHEN insufficient available Users exist to form a complete Group for a sport, THE Matching_Engine SHALL place those Users in a pending queue and SHALL NOT create an incomplete Group.
7. WHEN a User is placed in a pending queue, THE Notification_Service SHALL notify the User that matching is in progress and provide an estimated wait status.
8. WHEN a complete Group is formed, THE Matching_Engine SHALL trigger Group creation, captain assignment, and chat room creation within 5 seconds.

---

### Requirement 8: Captain Selection

**User Story:** As a group member, I want a captain to be assigned automatically, so that someone is responsible for coordinating the event.

#### Acceptance Criteria

1. WHEN a Group is created by the Matching_Engine, THE Captain_Selector SHALL assign exactly one User from the Group as Captain.
2. THE Captain_Selector SHALL use a weighted random selection that reduces the probability of selecting a User who has been Captain in their last 3 Groups.
3. WHEN a Captain is assigned, THE Notification_Service SHALL notify the assigned User that they are the Captain of the new Group.
4. WHEN a Captain has not confirmed the event within 2 hours of Group creation, THE Captain_Selector SHALL reassign the Captain role to another Group member and notify all Group members.
5. THE Captain SHALL have access to the following coordination actions: confirm the event, propose up to 3 venue options, finalize time and location, and mark participation confirmations.

---

### Requirement 9: Group Chat

**User Story:** As a group member, I want a real-time group chat, so that I can coordinate logistics and confirm participation with my teammates.

#### Acceptance Criteria

1. WHEN a Group is created, THE Chat_Service SHALL automatically create a dedicated chat room for that Group.
2. WHEN a User sends a message in a Group chat room, THE Chat_Service SHALL broadcast the message to all connected Group members within 500 milliseconds.
3. WHEN a User joins or leaves a Group, THE Chat_Service SHALL post a system message in the Group chat room (e.g., "Alex joined the group", "Sam left the group").
4. WHEN a Captain confirms an event, THE Chat_Service SHALL post a system message in the Group chat room (e.g., "Basketball match confirmed").
5. THE Chat_Service SHALL support message reactions using a predefined set of emoji (minimum: 👍 ❤️ 😂 🔥 👏).
6. WHEN a User opens a Group chat room, THE Chat_Service SHALL return the last 50 messages in chronological order.
7. WHEN a Group chat room has no messages, THE frontend SHALL display an empty state message prompting Group members to start the conversation.

---

### Requirement 10: Manual Event Creation

**User Story:** As a user, I want to manually create a sports event, so that I can organize activities on my own terms and invite others.

#### Acceptance Criteria

1. WHEN a User submits a new event with sport type, location, start time, and participant limit, THE Event_Service SHALL create the Event and add the User as the organizer.
2. THE Event_Service SHALL accept the following optional event fields: skill level requirement, price/cost per participant, and event description (max 500 characters).
3. WHEN an Event is created, THE Feed_Service SHALL include the Event in the home feed within 10 seconds.
4. WHEN a User requests to join a manually created Event with available capacity, THE Event_Service SHALL add the User to the participant list and notify the organizer.
5. WHEN a manually created Event reaches its participant limit, THE Event_Service SHALL mark the Event as full and prevent additional join requests.
6. WHEN a User cancels participation in an Event, THE Event_Service SHALL remove the User from the participant list and update the participant count.

---

### Requirement 11: Event Planning and Coordination

**User Story:** As a captain or organizer, I want venue suggestions and coordination tools, so that I can finalize event logistics efficiently.

#### Acceptance Criteria

1. WHEN a Captain requests venue suggestions, THE Location_Service SHALL call the AI_Service `POST /venue-recommendations` endpoint with the sport, participant count, and location, and return up to 5 venue options including name, estimated price, and distance in kilometers.
2. WHEN the AI_Service is unavailable, THE Location_Service SHALL return an empty venue list and display a message informing the Captain that AI suggestions are temporarily unavailable.
3. WHEN a Captain proposes venue options to the Group, THE Group_Service SHALL create a venue poll visible to all Group members.
4. WHEN Group members vote on a venue poll, THE Group_Service SHALL display live vote counts to all Group members via Socket.IO.
5. WHEN a Captain finalizes the venue and time, THE Notification_Service SHALL send a notification to all Group members with the confirmed location and start time.
6. THE Event_Service SHALL display the event location on an embedded map view using a publicly available mapping API.

---

### Requirement 12: Notifications and Real-Time Updates

**User Story:** As a user, I want real-time notifications for group activity, so that I stay informed without having to manually refresh the app.

#### Acceptance Criteria

1. WHEN a User is matched into a new Group, THE Notification_Service SHALL deliver a real-time in-app notification within 3 seconds of Group creation.
2. WHEN a Captain confirms an event, THE Notification_Service SHALL deliver a real-time notification to all Group members within 3 seconds.
3. WHEN a new message is posted in a Group chat room the User belongs to, THE Notification_Service SHALL deliver a real-time in-app notification if the User is not currently viewing that chat room.
4. WHEN an Event the User has joined is cancelled, THE Notification_Service SHALL deliver a real-time notification with the cancellation reason within 3 seconds.
5. WHEN an Event the User has joined starts within 1 hour, THE Notification_Service SHALL deliver a reminder notification.
6. WHEN a venue update is finalized for a Group the User belongs to, THE Notification_Service SHALL deliver a real-time notification with the updated venue details.

---

### Requirement 13: Maps and Location Assistance

**User Story:** As a user, I want to see event locations on a map and discover nearby venues, so that I can navigate to activities easily.

#### Acceptance Criteria

1. WHEN a User views an Event detail page, THE frontend SHALL display the event location on an embedded map.
2. WHEN a User enables location sharing in their profile, THE Location_Service SHALL store the User's coordinates and use them for proximity-based matching and venue discovery.
3. WHEN a User does not enable location sharing, THE Location_Service SHALL not require location data and SHALL allow the User to manually enter a city or area for matching purposes.
4. THE frontend SHALL display a privacy notice before requesting location access, explaining how location data is used.
5. WHEN a Captain requests nearby venues, THE Location_Service SHALL return venues within a 15 km radius of the event's location.

---

### Requirement 14: AI Service Health and Graceful Degradation

**User Story:** As a platform operator, I want the core application to remain functional when the AI service is unavailable, so that users are never blocked by AI failures.

#### Acceptance Criteria

1. THE AI_Service SHALL expose a `GET /health` endpoint that returns the service status, provider name, and model name within 2 seconds.
2. WHEN the AI_Service `GET /health` endpoint returns a non-200 response or times out after 3 seconds, THE backend SHALL mark the AI_Service as unavailable and serve all AI-dependent features in degraded mode.
3. WHILE the AI_Service is marked unavailable, THE backend SHALL continue to serve profile creation, availability declaration, matching, group chat, event creation, and notifications without interruption.
4. WHEN the AI_Service returns to a healthy state, THE backend SHALL automatically resume AI-enhanced features without requiring a restart.
5. WHEN an AI feature is unavailable, THE frontend SHALL display a non-blocking informational message (e.g., "AI suggestions are temporarily unavailable") rather than an error that prevents the User from completing their task.

---

### Requirement 15: Custom AI Feature — Smart Re-Engagement Reminders

**User Story:** As a user who hasn't been active recently, I want the platform to send me a personalized re-engagement reminder, so that I'm encouraged to get back to playing sports.

#### Acceptance Criteria

1. WHEN a User has not declared availability for 5 or more consecutive days, THE Notification_Service SHALL trigger the AI_Service to generate a personalized re-engagement message based on the User's sport preferences and past activity history.
2. WHEN the AI_Service generates a re-engagement message, THE Notification_Service SHALL deliver the message as an in-app notification within 24 hours of the inactivity threshold being reached.
3. WHEN the AI_Service is unavailable, THE Notification_Service SHALL send a generic re-engagement reminder (e.g., "It's been a while — ready to ShowUp2Move today?") instead of blocking the notification.
4. THE Notification_Service SHALL send at most one re-engagement reminder per User per 48-hour period to avoid notification fatigue.
5. WHEN a User declares availability after receiving a re-engagement reminder, THE Notification_Service SHALL not send another re-engagement reminder for the next 7 days.

---

### Requirement 16: Edge Case Handling

**User Story:** As a user, I want the platform to handle unexpected situations gracefully, so that I'm never left on a blank or broken screen.

#### Acceptance Criteria

1. WHEN no available Users exist for a given sport in the matching queue, THE Matching_Engine SHALL display a message to the User indicating that no matches are currently available and suggesting they check back later or create a manual event.
2. WHEN a User leaves a Group after it has been formed, THE Group_Service SHALL update the participant count, notify remaining Group members via the chat system message, and re-evaluate whether the Group still meets the minimum size requirement.
3. IF a Group falls below the minimum size requirement after a User leaves, THEN THE Group_Service SHALL notify all remaining Group members and offer them the option to remain in a new pending queue or cancel participation.
4. WHEN a Captain has been inactive for 2 hours without confirming the event, THE Captain_Selector SHALL reassign the Captain role as specified in Requirement 8, criterion 4.
5. WHEN a User's availability expires, THE Availability_Service SHALL remove the User from all pending matching queues and notify the User that their availability has expired.
6. WHEN a venue suggested by the AI_Service is no longer available, THE Event_Service SHALL allow the Captain to propose alternative venues without requiring a full event restart.
7. WHEN the frontend receives an unexpected API error, THE frontend SHALL display a descriptive error message and provide a retry action rather than showing a blank screen.
